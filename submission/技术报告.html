2、摘要

骑伴 AI 智能电动车中控屏面向电动车和两轮骑行场景，基于 Gemini-S1、openvela 与 LVGL，将车辆状态、离线地图导航、语音入口、音乐天气及主动安全提醒整合到 2.8 寸板载屏。系统以文件状态总线解耦 13 个板端模块，支持 UART/文件遥测、GPADC 电量、手机定位、离线瓦片和本地路网；板端规则 Agent 定义超速、低电量、疲劳、急停等 10 类 Skill。当前已生成可烧录固件并完成快应用构建验证，形成端侧优先、网络增强、断网可降级的骑行中控原型。

3、正文

3.1 绪论

3.1.1 项目背景与问题定义

传统电动车仪表通常只显示速度和电量，导航依赖手机，骑行过程中查看手机存在安全风险；弱网或断网时，在线地图和语音服务也容易失效。项目针对通勤骑手、校园和园区短途出行用户，将实时仪表、导航、语音入口和安全提醒集中到车载屏，并通过端侧规则维持基础能力。

3.1.2 技术难点

  • 在 R528 + 240×320 小屏上同时组织仪表、地图、语音、音乐和视频交互。
  • 统一车辆遥测、定位、导航、天气和多媒体状态，避免模块间强耦合。
  • 在弱网/断网条件下提供离线瓦片显示、本地路网规划与模拟数据兜底。
  • 将安全规则从被动展示提升为可配置、带优先级和冷却时间的主动触发。

3.1.3 创新点

  • 端侧主动安全：用速度历史、阈值、状态转换和冷却状态机实现超速、低电量、疲劳、急刹等主动提醒。
  • 文件状态总线：各服务通过 /data/qiban_*.json 原子交换状态，便于独立开发、故障隔离和模拟输入。
  • 在线/离线双路径：在线时可使用 HTTP 地图、天气与语音中转，离线时使用本地瓦片、路网和基础规则。
  • 一套数据、多种界面：原生 LVGL 为主界面，同时保留 Quick App 原型用于早期交互验证。

3.2.2 方案论证与选型

维度采用方案理由与备选对比
硬件Gemini-S1 / R528具备 openvela 基线、双核 Cortex-A7、显示/音频/网络和丰富外设，比纯 MCU 更适合复合 UI 与联网服务。
界面原生 LVGL 为主，Quick App 为原型LVGL 直接使用板载 LCD 与触控，启动链路更短；Quick App 保留用于页面原型和独立打包。
通信JSON 文件状态总线实现简单、可调试、模块故障互不拖累；代价是实时性和并发能力弱于消息总线。
地图离线瓦片 + 本地路网，在线 HTTP 增强断网仍可显示和规划；在线静态地图用于快速更新。
AI端侧规则 Agent确定性强、资源开销可控、无需持续联网；当前未接入 MiMo/LLM 推理。

端云职责：端侧负责采集、状态融合、UI、基础导航、规则提醒和多媒体；主机/服务端负责 ASR/TTS 作业中转、遥测保存与 OTA 文件分发。断网时语音云链路不可用，但仪表、离线地图、本地路网和本地规则可继续运行。

3.3 核心算法与技术原理

3.3.1 AI 算法实现

当前版本没有部署神经网络模型，也未接入 MiMo。AI 能力采用板端确定性规则 Agent：每秒读取车辆、导航和位置状态，维护 30 秒速度环形缓冲，计算均速和速度趋势，再逐一执行 Skill 的触发函数。Skill 带启用状态、优先级、阈值、时间窗口、触发次数和冷却时间，可从 NSH 命令行查看和调整。

Skill触发条件动作
overspeed速度 > 25 km/h语音/告警命令
low_battery电量 ≤ 20%语音 + UI 告警
fatigue连续骑行 ≥ 45 分钟休息提醒
nav_arrival / nav_turn到达或距转向点 ≤ 200 m导航播报
speed_trend持续减速趋势安全提示
ride_summary停车达到时间阈值骑行摘要命令
route_suggest骑行且未导航主动路线建议
weather_safety雨雪或大风语音 + UI 告警
emergency_stop2 秒内由 >15 km/h 骤降超过 12 km/h高优先级语音、告警、切页命令

完成度说明：上述 Skill 源码已存在，但当前默认固件配置未启用 Agent，动作消费者也未形成完整闭环；因此报告将其列为“已实现源码、未完成真机验收”。

3.3.2 关键机制

  • 原子状态发布：多数服务先写 .tmp，完成后 rename()，降低掉电或并发读取导致半文件的概率。
  • 多源融合与降级：车辆服务以模拟状态为基底，文件遥测优先覆盖，电量文件缺失时尝试 GPADC。
  • 离线路径规划：LVGL 离线地图组件加载瓦片和二进制路网，支持长按选点和本地路线渲染。
  • Skill 状态机：IDLE → FIRED → COOLDOWN，避免同类提醒每秒重复触发。

3.4 系统实现

3.4.1 软件/固件架构

项目使用 contest2026_110_hahaha.xml 将比赛仓模块映射进 openvela 的 packages/demos 与 packages/apps。板卡基线为 r528s3-gemini-s1/configs/nsh_minidisplay；辅助脚本修改 defconfig 和 rcS.nsh，配置服务开机启动。仓库现有 13 个板端模块目录、一个 Quick App、一个 FastAPI 服务端及共享 JSON Schema。

3.4.2 数据流与关键流程

每 1 秒：
传感器/模拟值 → vehicle_service → vehicle_state.json
                                 ↓
location.json → nav_service → nav_state.json → map_service
      │                          ↓              ↓
      └──────────────────────→ qiban_ui ← map state / 离线瓦片

Agent 路径：
vehicle/nav/location JSON → 速度历史与状态分析 → Skill 条件判断
→ 语音/UI/导航/告警命令 JSON → 对应服务（当前闭环未全部完成）

3.4.4 应用与交互

原生 UI 在 Tileview 中组织仪表、离线地图、语音/天气、音乐和媒体浏览界面。仪表显示速度、电量、续航、时长、里程和告警；地图支持缩放、平移、定位标记和长按选终点；语音页支持预设目的地和中文输入。Quick App 保留首页、导航页、助手页三页原型。

3.4.5 自定义 Skill

仓库沉淀了 10 个 C 语言 Skill，入口位于 app/qiban_ai_agent/src/skills/，由注册表按 Kconfig 条件编译。它们覆盖安全、导航和骑行总结场景。赛事要求的 /data/agent/skills/ 运行时 Skill 定义尚未完成，当前实现是静态编译形式。

3.7 总结与展望

项目已形成面向两轮出行的 openvela 中控原型：板端服务、LVGL 多页面 UI、地图导航、语音与多媒体代码、规则 Agent、服务端和 OTA 工具均有源码，核心模块曾成功编译为 R528 NAND 镜像。其价值在于把传统仪表升级为可扩展的主动服务终端，并兼顾断网场景。

目标受众：城市通勤、校园/园区骑行用户，以及电动车整车厂和智能仪表方案商。商业模式：可作为整车前装中控、存量车辆后装终端或软硬件 SDK 授权方案；离线地图和模块化服务有利于面向不同车型裁剪。

不足：Agent 未进入默认固件，运行时 Skill 规范、真实车辆协议、完整语音闭环、release.rpk、实物视频和量化测试均未完成。后续应优先完成配置收敛和真机验收，再补功耗、时延、连续运行与告警准确率数据，最后评估 MiMo/LLM 在骑行摘要和复杂意图理解中的必要性。
